# Production pg pool size: 1 → 3

**Decision:** set `PG_POOL_MAX=3` on Vercel Production. This is Anik's change, made when he says so.

## Why

On Vercel `poolLimits()` (`server/src/db.js`) gives each function instance one connection unless `PG_POOL_MAX` is set, and it is not set. With one connection, every `Promise.all` in the API runs its statements one after another.

On 20 Nov 2026 the small readiness statements executed in 0.1–2.2 ms each (`pg_stat_statements`), but each cost about 11 ms of round trip. Job Cards spent 368 ms of server time on 19 statements.

A pool of 3 lets a wave of independent statements cost one round trip instead of one per statement. The `perf/fewer-round-trips` branch cuts the waves; on live data, read-only, with a pool of 3:

| Endpoint | Waves before → after |
|---|---|
| Job Cards | 12 → 8 |
| Planning | 15 → 4 |
| Station pages | 15 → 7 |
| Print Planning | 14 → 7 |
| Artwork | 11 → 7 |

Every one of those answers is byte-identical.

## What an escaped statement does once the pool is bigger

A function handed a transaction's client (`qc` / `oc` / `client`) must run every statement on that client. One that calls the module-level `q()` / `one()` instead escapes the transaction:

| Pool | What happens |
|---|---|
| **1 (today)** | It waits for the only connection, which the transaction holds. After 10 s: `timeout exceeded when trying to connect`. Loud, and the transaction rolls back. |
| **3, escaped read** | It reads outside the transaction and does not see the transaction's own uncommitted writes. The decision is made on stale data, silently. |
| **3, escaped write** | It commits on its own and survives the transaction's rollback, leaving half an operation in the database. |
| **3, escaped statement on a locked row** | It waits on a row lock held by the very transaction that is waiting for it. Postgres cannot see that deadlock, so it hangs until `statement_timeout` or Vercel's `maxDuration` of 30 s. |

So **pool > 1 is safe only while no statement escapes.** That is what `server/src/no-pool-escape-in-tx.test.js` keeps true:
- **What it scans:** 744 functions handed a transaction client, in every shape one is written: `function f(qc)`, `async (qc, oc) =>`, `qc =>`, expression-bodied arrows, method shorthand, and nested default parameters. Shapes test included.
- **What it finds today:** none.
- **Proven to fail:** on an escape planted in `readinessBatch`, and on one planted in a real `tx(async qc => …)` callback.

**It does not see indirect paths:** an alias such as `const db = q`, a direct `pool.query`, or a helper that falls back to `q` when it is not handed a client. Code review must still catch those.

`tx()` itself still holds one connection for its whole transaction, so its statements stay ordered on that client.

## Connection budget (20 Nov 2026, `pg_stat_activity`)

| | |
|---|---|
| `max_connections` | 60 |
| In use | 30 |
| Supavisor server connections | 12 |
| Supavisor mode and `pool_size` | **Anik to read** from Supabase → Database → Connection pooling |
| Vercel **Fluid compute** for `ci-plant` | **Anik to read** from Vercel → Project → Settings → Functions. The connector does not expose it. |

The right model depends on Fluid compute.

- **Fluid off:** each instance serves one request at a time. The budget is 3 × peak instances. A one-plant ERP runs a handful of warm instances, so about 15 client connections.
- **Fluid on:** one instance serves many requests at once and they share its pool.
  - Today, pool 1 means every request on a busy instance also waits behind any other request's statements, and behind a whole `tx()`.
  - Pool 3 helps there too.
  - The connection count stays at most 3 per instance, but Supavisor sees fewer, busier clients.

Either way, Supavisor's transaction mode multiplexes clients onto its server pool, so this does not add Postgres backends one-for-one.

**Rule:** 3 × peak instances must stay at or below half of Supavisor's client limit.

## How to tell it worked

Every response carries `Server-Timing: db;dur=…;desc="N q", app;dur=…`.
- After the change, `app` on Job Cards should drop while `N q` stays 19.
- If `db` (the sum of statement times) rises sharply instead, statements are queueing at Supavisor. Set `PG_POOL_MAX` back to 1.
- Measure warm loads apart from the first load after a pause. With `idleTimeoutMillis` 10 s, the pool empties when idle, and the first wave after a gap opens up to three new connections at once.
